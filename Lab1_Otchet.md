## Цель работы

Получить практический опыт разработки защищённого backend-приложения с автоматизированной проверкой кода на уязвимости. Освоить принципы защиты от OWASP Top 10 и интеграцию инструментов безопасности в процесс разработки (CI/CD).

## 1. Выбор стека и описание API

Для реализации был выбран язык Python и микрофреймворк Flask. Проект инициализирован как git-репозиторий и связан с удалённым репозиторием на GitHub. Данные хранятся в базе SQLite.

API реализует мини-блог и содержит следующие методы:

| Метод | Эндпоинт | Доступ | Назначение |
| --- | --- | --- | --- |
| POST | /auth/register | открытый | Регистрация пользователя (пароль хэшируется) |
| POST | /auth/login | открытый | Аутентификация, выдаёт JWT-токен |
| GET | /api/data | только с токеном | Получение списка постов |
| POST | /api/posts | только с токеном | Создание поста (третий метод) |

Эндпоинты /api/data и /api/posts защищены: доступ к ним возможен только при наличии действительного JWT-токена.

## 2. Реализованные меры защиты

2.1. Защита от SQL-инъекций (A03:2021 Injection). Все обращения к базе данных используют параметризованные запросы (prepared statements): значения подставляются драйвером отдельно от текста SQL и не склеиваются со строкой запроса. Конкатенация строк для формирования SQL не применяется. Поэтому ввод вида ' OR '1'='1 воспринимается как обычное значение логина и не изменяет логику запроса.

```
db.execute("SELECT password_hash FROM users WHERE username = ?", (username,))
```

2.2. Защита от XSS. Весь пользовательский текст перед сохранением и выдачей экранируется функцией markupsafe.escape(). Опасные символы (<, >, &, ") заменяются HTML-сущностями, поэтому нагрузка <script>alert(1)</script> превращается в безопасный текст &lt;script&gt;... и не исполняется в браузере.

2.3. Защита от Broken Authentication (A07:2021). Пароли никогда не хранятся в открытом виде — только в виде bcrypt-хэша со случайной солью. После успешного входа сервер выдаёт подписанный JWT-токен (алгоритм HS256) со сроком жизни 60 минут; секрет подписи берётся из переменной окружения и не хранится в репозитории. Специальный middleware-декоратор проверяет токен на всех защищённых эндпоинтах и возвращает 401 при его отсутствии, истечении или подделке.

## 3. Настройка CI/CD pipeline

В корне проекта создан файл конфигурации GitHub Actions (.github/workflows/ci.yml). Проверки запускаются автоматически при каждом push и при создании pull request и включают три шага:

- SAST — Bandit: статический анализ исходного кода Python на типовые уязвимости.
- SCA — pip-audit: анализ зависимостей из requirements.txt на известные уязвимости (CVE) по базе OSV.
- Тесты — pytest: функциональные тесты и тесты безопасности (проверка SQLi, XSS, запрета доступа без токена).

Отчёты инструментов сохраняются как артефакты запуска. По результатам прогона критических уязвимостей не обнаружено, все проверки пройдены успешно.

## Ответы на контрольные вопросы

1. Почему хэширование пароля с помощью алгоритмов вроде bcrypt предпочтительнее SHA-256? bcrypt — медленный адаптивный алгоритм с настраиваемой сложностью (work factor) и встроенной случайной солью. Медлительность делает перебор паролей дорогим, соль защищает от радужных таблиц и делает одинаковые пароли разными хэшами. SHA-256 рассчитан на скорость, поэтому на GPU перебирается миллиардами хэшей в секунду и без соли уязвим к готовым таблицам — для хранения паролей он не подходит.

2. В чём основная разница между SAST и DAST? SAST (статическое тестирование) анализирует исходный код приложения, не запуская его, — это «взгляд изнутри», позволяет находить проблемы рано, но даёт ложные срабатывания. DAST (динамическое тестирование) проверяет уже работающее приложение снаружи, как «чёрный ящик», отправляя ему запросы, — находит ошибки конфигурации и поведения в рантайме, но не видит исходный код.

3. Опишите механизм работы JWT-токена. JWT состоит из трёх частей в кодировке base64url: заголовок (header), полезная нагрузка (payload) и подпись (signature). В payload хранятся claims — например, идентификатор пользователя (sub), время выпуска (iat) и истечения (exp). Сервер подписывает токен секретным ключом (HMAC для HS256). При каждом запросе сервер пересчитывает подпись своим секретом и сравнивает её: если подпись совпадает и срок не истёк, токен подлинный. Данные хранятся у клиента, поэтому сервер не держит сессию (stateless).

4. Какие риски возникают, если не проводить аудит сторонних библиотек? В зависимостях могут быть известные уязвимости (CVE) — это атака на цепочку поставок (supply chain). Уязвимая версия библиотеки может привести к удалённому выполнению кода, утечке данных или обходу аутентификации уже в вашем приложении, хотя ваш собственный код написан правильно. Поэтому зависимости нужно регулярно сканировать (SCA) и своевременно обновлять.

## Вывод

В ходе работы разработан защищённый REST API на Flask с реализацией мер против SQL-инъекций (параметризованные запросы), XSS (экранирование вывода) и Broken Authentication (JWT + bcrypt). Настроен CI/CD pipeline в GitHub Actions с автоматическим запуском SAST (Bandit), SCA (pip-audit) и тестов при каждом изменении кода. Проверки проходят успешно, критических уязвимостей не выявлено.
